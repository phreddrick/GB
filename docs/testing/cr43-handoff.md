# CR-43 handoff: durable maintenance mode and process readiness (ADR-0010)

Branch `feature/durable-maintenance-mode` (from `master` `194592c6`), 2026-11-08. Not deployed; independent review and hosted CI pending; acceptance on the development server needs its own authorisation.

## 1. Root cause

The Stage 3 image upgrade of 2026-11-08 (`docs/testing/phase2-validation.md` section 9.3, evidence `cr18-image-upgrade-2026-11-08`) synced successfully in Argo CD and then stalled: the quiesced Pod answered `/readyz` 503, Kubernetes 1.36's `OrderedReady` StatefulSet controller returns from `processReplica` while a Pod is not Running and Ready and never reaches the rolling-update deletion, so the old Pod stayed. Quiescing was also only an in-memory mode: the replacement (created after an owner-authorised guarded deletion) started `SERVING` and had to be quiesced again inside the ten-minute no-catch-up window.

## 3. Persistence format and compatibility

- `meta/maintenance` = `{"schema_version":1,"quiesced":true,"set_at":"<RFC3339>","reason":"operator quiesce (admin API)","engine_version":"<module@rev>"}`; strictly decoded like the commit and schedule records (presence of every required key, no unknown key, no JSON null, no trailing data) and validated (`schema_version 1`, `quiesced true`, non-zero `set_at`).
- Absent record: pre-CR-43 behaviour exactly (`TestStoreWithoutMaintenanceRecordKeepsStartupBehaviour`, with and without a CR-18 commit record).
- Forward: an engine without ADR-0010 ignores the extra key (bbolt bucket entries are independent) and starts `SERVING` as it always did; the record remains and a later ADR-0010 engine honours it. Rolling back the image therefore loses the durable quiesce but never the data.
- The record is outside `WorldDigest`, so a quiesce does not change the logical world state; a resume changes only the schedule fields that the digest already includes (the no-catch-up reschedule), exactly as before this change.
- A bbolt transaction that reports an error has not necessarily been rolled back (the meta page may be written before a failing final fsync), and a change that is visible after such an error has not been confirmed durable either. Both maintenance writes therefore take a before-snapshot (raw record and schedule bytes, and whether the record present had been confirmed by a successful transaction of this process or read at startup), and on failure compare the store **byte for byte** with that snapshot and with the exact bytes the transaction intended to write (`classifyMaintenanceWriteFailure`, `classifyResumeFailure` in `internal/game/maintenance.go`; `db.EncodeMaintenanceRecord`, `db.EncodeScheduleRecord`). Timestamps are never used as a transaction identity. The in-memory durability claim is lowered to the most pessimistic reading the store supports and never raised by a failed write; the test-only fault stages `maintenance.*.committed` reproduce the "visible but reported failed" shape, `maintenance.clear.in-tx` the rollback, `meta.get` a failing read-back.

## 4. Crash consistency and ordering

| Point of failure | Store afterwards | Next start |
|---|---|---|
| crash before the quiesce's record transaction commits | no record | `SERVING` (the caller got no success; status after the start says so) |
| crash after the record committed, before the mode changed or the reply was sent | record | `QUIESCED` |
| record write reports an error | the engine reads the store back and reports what it found: **no record** → next start would be `SERVING`; **this record visible** → *likely* `QUIESCED`, durability on disk not confirmed; **the record held before, unchanged and valid** → `QUIESCED` if an earlier successful write had confirmed it (not reachable through the actor, where a confirmed record makes quiesce a no-op), otherwise likely, not guaranteed; **malformed bytes** → the next start would halt `CORRUPT_STORE`; **bytes matching neither state** → unpredictable, inspect; **read-back failed** → unknown. In every case the engine is `QUIESCED` in memory, `maintenance.durable false` with the explanation, `gb_maintenance_durable 0`, exit 5 to `gbctl` | as reported; re-issue `quiesce` to confirm durability (a repeat in the same process writes again) |
| orderly shutdown while quiesced (shutdown commit) | record kept, new commit record of kind `shutdown` | `QUIESCED` |
| crash before the resume transaction commits | record and old schedule | `QUIESCED` |
| crash after the resume transaction committed | no record, rescheduled schedule | `SERVING` (the resume was durable; `next_update` is the rescheduled one) |
| resume transaction fails, store **unchanged** (read-back equals the before-snapshot byte for byte) and the record was **confirmed** durable | record and old schedule; engine `HALTED`, `maintenance.durable true` kept | `QUIESCED` |
| resume transaction fails, store unchanged, but the record was **never confirmed** (it became visible through an earlier failed write) | unchanged; engine `HALTED`, `maintenance.durable false`, error says likely `QUIESCED`, not guaranteed | likely `QUIESCED` |
| resume transaction fails, store unchanged and **no record** (the quiesce was in memory only) | unchanged; `HALTED`, `durable false`, error says `SERVING` | `SERVING` |
| resume transaction reports an error but the resume **is visible** (record gone, the schedule bytes this resume intended) | the resumed pair, durability on disk unconfirmed; engine `HALTED`, claim withdrawn (`durable false`), `gb_maintenance_durable 0`; error says `SERVING` if the change persisted, otherwise `QUIESCED` from the previously **confirmed** record, or "possibly QUIESCED, not guaranteed" when that record had never been confirmed either | `SERVING` if persisted, else `QUIESCED` (confirmed prior) or not guaranteed (unconfirmed prior) |
| resume transaction fails and the read-back fails, or the store matches neither state | engine `HALTED`, `maintenance.durable false`, error says unknown / unpredictable | unknown until the next start; `gbctl status` then says |
| malformed record | untouched | `HALTED` `CORRUPT_STORE`, not Ready, nothing written |

The maintenance writes are ordinary fenced writes: a turn body cannot perform them (`TestMaintenanceWritesAreFencedAndIndependentOfCommits`), and a quiesce requested during a turn runs after the turn's commit on the actor (`TestQuiesceDuringTurnIsAppliedAfterTheCommit`).

## 5. Readiness by mode

| Mode | `/readyz` | `game_ready` | `/livez` |
|---|---|---|---|
| `STARTING` | 503 | false | 200 |
| `UNINITIALIZED` | 200 | false | 200 |

| `QUIESCED` | **200** (`maintenance true`, `maintenance_durable` when the record is held) | false | 200 |
| `HALTED` (incl. `CORRUPT_STORE`) | 503 | false | 200 |

Startup and liveness probes are unchanged in the manifests; the startup probe is satisfied by the first 200, which a quiesced start gives at once.

### 6.2 Hosted CI (pull request #18)

The first two hosted runs of the branch head `7ff59da` (42527820295 and 42527827925; the first also failed the acknowledgment gate because it started before the `gate-change-reviewed` label was applied, which the second run passed) failed only in the kind job, at the controller-ownership assertion of the rolling-update step. The owner's reading of the logs showed that every check of the step before that assertion had passed: the quiesced Pod stayed Ready through the 20 s hold, `rollout status` completed, the replacement had a new UID on the expected image tag with converged revisions, the PVC UID was unchanged, the new Pod had no restarts, and a `SuccessfulDelete` event from the `statefulset-controller` was present. The checks after the assertion (orderly `QUIESCED` shutdown of the old Pod, `starting QUIESCED` and no turn in the new one, status, counters, `next_update`, universe, `/readyz`, resume) did not run in those two runs because the step failed before them; the rerun must show them.

Root cause: the inline jq filter required the message `delete Pod gb-engine-0 in StatefulSet gb-engine successful`, but `recordPodEvent` in `pkg/controller/statefulset/stateful_pod_control.go` (v1.36.4) title-cases the verb (`cases.Title`), so the controller writes `Delete Pod gb-engine-0 in StatefulSet gb-engine successful`, and jq's `test` is case-sensitive. The hosted log of run 42527827925 (retrieved by the owner; the API refuses log downloads without repository admin rights and the web log endpoints need a session, so igor could not read it) printed the rejected event as `{"uid":"d8899d68-b1e5-446d-9906-d034120ef272","comp":"statefulset-controller","at":"2026-11-08T22:01:50Z","msg":"Delete Pod gb-engine-0 in StatefulSet gb-engine successful"}` followed by `FAIL … after 2026-11-08T22:01:48Z`: the component matched, the instant was two seconds after the rollout began, and the message differed from the filter only in the case of the verb. The UID in the dump is the event's `involvedObject.uid` only; the excerpt does not carry the expected StatefulSet UID the script had read before the rollout, so that the UID predicate held is an inference (the tag change updates the StatefulSet in place and never recreates it), not an observation. The corrected check prints both values, so a rerun settles it. The same event shape was confirmed from the Stage 3 evidence of the same controller on the development cluster (`SuccessfulCreate`, `Create Pod … successful`, `source.component statefulset-controller`, `lastTimestamp` at second precision), and the per-predicate comparison was reproduced offline against it. That event is now a fixture of the regression tests.

Correction: the filter moved to `.github/scripts/sts-controller-delete-event.jq`, which evaluates the four predicates separately, compares the message case-insensitively (both verb casings are written by the same controller), parses `lastTimestamp` or `eventTime` as a calendar-valid RFC 3339 UTC instant at second precision (an unparseable or normalised value such as `22:05:61` fails the time predicate), errors with no output on a `since` that is not a calendar-valid second-precision UTC instant or on an input that is not an EventList, and returns exactly one `{expected, candidates, matched}` report. The script compiles the program before `kind create cluster`, requires exactly one report object with a `matched` array (no output, several values or a non-report fail the step rather than slipping past the count), decides on a non-empty `matched`, prints `expected`/`observed`/`ok` for every predicate of every candidate event on failure, copies `events-rollout*.json` into the diagnostics artifact, and keeps every other check of the step unchanged (new Pod UID, image, converged revisions, same PVC, zero restarts, orderly `QUIESCED` shutdown of the old Pod, `starting QUIESCED` in the new one, no `turn starting`, no `CORRUPT_STORE`, status `QUIESCED` durable, counters, `next_update` and universe unchanged, `/readyz` of the replacement). Regression tests: `test_sts_delete_event.py` (the program on synthetic events, and the script's own block extracted and run under `set -euo pipefail`). What the event proves is qualified in the program's header: Kubernetes records `SuccessfulDelete` also when the controller's request finds the Pod already gone, and the message names the Pod rather than its UID, so the event together with the job's controlled sequence (nothing else deletes a Pod in the kind job) is the evidence that no manual deletion was needed; it is not an audit-grade proof of who deleted.

## 8. Outstanding risks

- The kind proof runs only on hosted runners; it exercises the controller mechanics with kind's local-path RWO volume, not Longhorn RWOP attachment transitions (those were observed in Stage 3: reused on the same node).
- A quiesced Pod is now routable: players can connect and log in (CR-20) and receive the paused refusal. Acceptable for development with `GB_ENROLL_PREVIEW=false`; revisit with the player-access decision.
- Monitors keyed on `/readyz` for gameplay must switch to `game_ready` or `gb_engine_mode`.
- `gbctl` from an older revision cannot decode the new status (strict envelope); build it from the deployed revision as the runbook already requires.
- A `CORRUPT_STORE` start caused by a malformed maintenance record requires operator inspection of `meta/maintenance`; no repair tool exists (consistent with the commit-record policy). Such a start never answers `/readyz` 200, so in Kubernetes the **startup probe** (120 × 5 s) restarts the container after about ten minutes even though `/livez` stays 200; the restart changes nothing (nothing is written) and the inspection happens through `kubectl logs --previous` and the admin API during the ten-minute window, or by scaling to zero and inspecting the volume elsewhere (owner decision; this is the pre-existing behaviour of every `HALTED` start, not new to CR-43).
- The in-process test fault hook cannot exercise a crash *between* the transaction's commit and the reply (the subprocess tests crash before or after whole operations); the ordering argument for that boundary is by inspection: the record write precedes the mode change and the reply, and the resume transaction precedes the mode change and the reply.
