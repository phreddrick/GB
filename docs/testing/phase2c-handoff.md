## 5. Container build and runtime validation design

Build (both `ci` and the publish job): `docker/build-push-action` with `context: go`, `file: deploy/docker/Dockerfile`, `target: server|gbctl`, `platforms: linux/amd64`, `push: false`, `provenance: false`, `sbom: false`, no `cache-from`/`cache-to` (nothing a pull request can poison; the privileged job never reads a cache), `SOURCE_DATE_EPOCH` from `git log -1 --format=%ct`, exporter options `rewrite-timestamp=true`, OCI labels `title`, `source`, `revision` (`github.sha`), `version`, `created` (commit time). `ci` writes two exporters per target from one build (`type=oci` tarball for the downstream jobs and `type=docker` tarball for the engine checks); the publish job writes the OCI tarball only. Buildx multi-exporter output needs Buildx and BuildKit 0.13 or later (runner Buildx 0.38.1; `setup-buildx-action` starts a current `moby/buildkit:buildx-stable-1` container).

`image-checks.sh` asserts, per target, the twelve requirements of brief section 5: (1) the archive holds exactly one `linux/amd64` OCI image manifest and all blobs re-hash to their digests (`oci_digest.py`); (2) the docker-loaded image's `Id` equals the archive's config digest, so the engine checks run on the same artifact; (3) `Config.User` is `65532:65532`, entrypoint is the binary; (4) the exported rootfs contains the binary, not the other target's binary (distinct images), no `sh`, `bash`, `busybox`, `apt`, `dpkg` or `apk`, no `.git`, key, `.env`, `.netrc`, Docker config, `.db`, `go.mod` or `go.sum`, and `/etc/passwd` has `nonroot:x:65532:65532`; (5) the binary is a static ELF64 x86-64 (no `PT_INTERP`), `go version` reports the pinned `go1.27.3`, `go version -m` shows `-trimpath=true`, `CGO_ENABLED=0`, `GOOS=linux GOARCH=amd64` and no `vcs.revision`; (6) `docker run --entrypoint /bin/sh` fails with "not found"; (7) the server starts `--read-only --user 65532:65532 --cap-drop ALL` with a tmpfs volume and answers `/readyz` 200 `UNINITIALIZED game_ready=false`, `/livez` 200, admin 401 without a token; (8) the `gbctl` image, on the host network, gets `status` `UNINITIALIZED` with the right token and exit 3 with a wrong one; (9) `docker stop` yields exit 0 and `shutdown complete`, and neither secret appears in the log; (10) a start without secrets exits non-zero; (11) the record (`image-build-record.json`) carries digests, config digests, sizes, Go version, commit, run URL and epoch; (12) secrets are random per run, exported to the container only, never printed. The two images' manifest and config digests must differ.

Source context: `go/` filtered by `go/.dockerignore` (unchanged), so nothing from `source/`, `docs/` or the repository root enters the build; the rootfs check (4) is the runtime assertion of that.

## 6. Image scanning and SBOM

Trivy v0.76.1 (`aquasecurity/trivy-action` pinned; `TRIVY_DB_REPOSITORY` lists the ECR public mirror before GHCR to avoid anonymous rate limits) scans **both final OCI archives** (`--input`, not the builder image) with `scanners: vuln,secret`, all severities, `ignore-unfixed: false`, `exit-code: 0`, JSON output. The action fails the job on a scanner error (empty or missing report is also a failure: `test -s`). `trivy_policy.py` then evaluates the reports: **fail on any CRITICAL finding with a non-empty `FixedVersion` and on any secret**; print a severity table split into fixable and unfixable; append it to the step summary; exit 2 (not 0) on a malformed report. Unfixable CRITICAL findings and every HIGH or lower finding are reported, counted and kept in the 90-day artifact, not suppressed; the plan's "Critical-fixable" policy is applied without exceptions. Expected baseline for a distroless static image: zero OS packages beyond `base-files`, `netbase`, `tzdata` and CA certificates, plus the Go module graph of the binary (bbolt, gorilla/websocket, golang-jwt, x/crypto, x/sys, x/term); govulncheck in the `go` job already proves no reachable Go vulnerability at the same commit.

Syft v1.55.0 (`anchore/sbom-action/download-syft` pinned; the sub-action only installs the binary) produces one SPDX JSON SBOM per image from the OCI archive, with `--source-name` and `--source-version` set to the image name and manifest digest; package counts go to the summary; the files are the `sboms` artifact (90 days) in `ci` and part of the `publish-<sha>` artifact in the publish job. Nothing generated is committed.

Deferred, with the reason: attaching the SBOM to the image as an OCI referrer and SLSA provenance attestations (both would turn the pushed artifact into an index and change the digest model; ADR-0006 amendments), cosign keyless signing (plan Decision 6), a Trivy SARIF upload to code scanning (would need `security-events: write`; the JSON artifact and summary serve the single maintainer), scanning on a schedule (new vulnerabilities in an already published image are caught at the next publication; a nightly scan is a one-line `schedule` trigger that the policy check currently forbids on purpose, pending the owner's decision).

## 9. GHCR publishing design and permissions model

`publish-images.yml` has exactly one trigger, `workflow_dispatch`, with inputs `confirm` (must equal `publish`) and `open_digest_pr` (boolean, default false); `concurrency: ghcr-publish` without cancellation; top-level `permissions: contents: read`.

| Job | Permissions | Guards |
|---|---|---|
| `preflight` | `contents: read`, `actions: read` | typed confirmation; `GITHUB_REF == refs/heads/master`; commit is an ancestor of `origin/master`; **one** run of `.github/workflows/ci.yml` resolved through `GET /repos/phreddrick/GB/actions/workflows/ci.yml/runs?head_sha=<sha>` whose `repository`, `head_repository`, `path`, `head_sha`, `head_branch=master`, `event=push` match, `status=completed`, `conclusion=success`, exactly one such run (none or several: refused); then `GET .../actions/runs/<id>/attempts/<n>/jobs` and every one of the seven required job names present exactly once with `run_id`, `run_attempt` and `head_sha` of that run and `completed/success` (`ci_provenance.py`; policy in its docstring; GB2C-02) |
| `publish` | `contents: read`, `packages: write` | `if: github.ref == 'refs/heads/master' && inputs.confirm == 'publish'`; `environment: ghcr-publish`; rebuilds both targets with the section 5 settings; `oci_digest.py` asserts single-manifest, `linux/amd64`, user 65532, revision label equals the commit; Trivy with the same policy **before** any push; `docker/login-action` with `GITHUB_TOKEN`; `publish-push.sh` |
| `digest-pr` | `contents: write`, `pull-requests: write`, `packages: read` | `if: inputs.open_digest_pr == true`; calls `digest-update-pr.yml` with the server digest from the publish job's output and `github.sha` |

`publish-push.sh` extracts each OCI tarball to a layout directory and runs `crane push <dir> ghcr.io/phreddrick/<image>:<sha>`; crane uploads the manifest bytes unchanged, so `crane digest` of the pushed tag must equal the archive's manifest digest, or the job fails. It then fetches the manifest by digest (retrievability), checks the media type is a single OCI image manifest, reads the config (platform, user, `revision` label equals the commit), and only when **both** images verified tags both `master` and checks the tags resolve to the digests. The publish record (`publish-record.json`, schema `gb-publish-record` version 2, in the `publish-<sha>` artifact with the Trivy reports and SBOMs, 90 days, also in the step summary) is rendered from `publish-record.jq` into a temporary file, validated by `publish_record.py` (schema, both images, repository names, target, source commit, digest forms, `verified` implies published digest equals the archive digest re-read from the archive, `pull` equals `repository@digest`, tags, `status`/`complete`/`master_tag_applied` consistency with the per-image states, and agreement with the publisher's own view) and only then moved into place. It carries `status` (`published`, `partial`, `failed`), `complete`, `master_tag_applied`, per image `state` (`not_pushed`, `push_failed`, `pushed_unverified`, `verified`), local and published manifest digests, config digest, size, tags and pull reference, and a `published` list of everything that reached the registry. Outcomes: `published` prints `publish-push: ALL PASS`, exits 0 and exports the digests; anything pushed but not fully verified and tagged is `PARTIAL_PUBLICATION`, exit 1, identifiers preserved, no `master` tag, no outputs (so the `digest-pr` job, which `needs: publish`, never runs); nothing pushed is `FAILED`. A record that cannot be rendered, validated or moved fails the run even after both images verified, and the message still names what was published. The jq program is compiled before the first push. Operator procedure for a partial release: `bootstrap.md` section 2 (GB2C-01).

**Digest kind.** With `provenance=false`, `sbom=false` and one platform, buildx produces no image index; the published artifact is one platform-specific OCI image manifest and its digest is the deployment identity. Kustomize references that digest (`validate.py` already enforces the `@sha256:` form). If attestations are ever enabled the pushed object becomes an index and the digest to pin would be the index digest; `oci_digest.py`, `verify-published-image.sh` and `publish-push.sh` all refuse an index today so that change cannot happen silently.

**First publication policy (recommended, owner-driven):** merge the Phase 2C pull request after its hosted `ci` run and the independent review; optionally add protection to the `ghcr-publish` environment (a required reviewer and a deployment-branch rule allowing `master` only; GitHub creates the environment unprotected on first reference); dispatch `publish-images.yml` on `master` with `confirm=publish` and `open_digest_pr=false`; review the run (digests equal to the `ci` build record of the same commit are expected but not required), make both packages public, verify anonymous pulls, then dispatch `digest-update-pr.yml` by hand with the server digest and the commit, or rerun the publish with `open_digest_pr=true`. **Automatic publication on every master push is not configured** (Decision 31). GHCR creates packages as private; the one-time visibility change is the owner action in `bootstrap.md` section 2; if kept private an `imagePullSecret` becomes a third out-of-band Secret.

Every check exits 1 with the reason (seven negative cases run locally, section 12).

3. If `gh pr create` fails, the job **fails** after printing the compare URL and the owner action (repository setting "Allow GitHub Actions to create and approve pull requests", or open the pull request by hand). Whether this repository permits token-created pull requests is **unverified** from the development host; nothing assumes it and no other token exists.

Distinctions, stated for the operator (GB2C-05; GitHub docs "GITHUB_TOKEN", section "When `GITHUB_TOKEN` triggers workflow runs", <https://docs.github.com/en/actions/concepts/security/github_token>): (1) *permission to create* the pull request is the repository setting above; (2) the `opened` event of a pull request created with `GITHUB_TOKEN` creates the `ci` workflow run in an **approval-required** state, and a maintainer starts it by selecting **Approve workflows to run** in the merge box (a label does not approve anything; `labeled` from the token creates no run); (3) the *required status checks* then execute on the one-line change and must pass; (4) *acknowledgment labels* are a separate gate for protected tooling and are not needed (the digest file is not protected tooling); (5) *review and merge* are a human decision under the ruleset; *synchronisation* of `gb-dev-server` is a separately approved manual Argo CD action (`deploy.md` section 2). The manual fallback (open the pull request by hand from the pushed branch) is retained; no personal access token or GitHub App is introduced to bypass the approval. The pull request body and the job summary state this sequence. The StatefulSet, the frozen identity and the live cluster are untouched by every step; the sentinel comment above the digest line is left for the human reviewer to update.

## 11. Reproducibility, failure handling and workflow safety

Reproducibility, stated exactly (ADR-0006 amendments, `deploy/docker/README.md`): repeatable source build (pinned toolchain, `go mod verify`, `-mod=readonly`); binary expected byte-identical per commit (`-trimpath -buildid=`, no VCS stamp); layers and manifest expected identical per commit (`SOURCE_DATE_EPOCH`, rewritten timestamps, `created` label from the commit); the OCI manifest digest is the identity; SBOM and provenance are kept out of the pushed object. Digest equality between the `ci` build record and the publish record of the same master commit is to be **observed and recorded** at the first publication; it is not asserted by any job and not claimed here. On pull requests the checked-out commit is the merge commit, so digests differ from the branch head's by construction.

Failure handling (brief section 11): a build failure fails the `docker` job; image start failure, non-root or read-only violation and missing-secret acceptance fail `image-checks.sh`; failed initialisation, failed deployment, unmet readiness and a surviving cluster fail `kind-e2e.sh` (and the workflow's own `if: always()` check); a scanner error or empty report fails the scan step before the policy; a policy violation fails `trivy_policy.py` (exit 1) and a missing, empty, truncated, malformed or wrong-image report exits 2 (every result and finding collection must have the type Trivy v0.76.1 emits, at least one result section must exist, `ArtifactName` and `Metadata.ImageID` must be the built archive and its config digest; GB2C-03); an invalid or missing digest fails `set_image_digest.py` (exit 1/2), `verify-published-image.sh` and `publish-push.sh`; failed registry authentication fails `docker/login-action` or the first `crane push`; a failed publication is `status: failed`, a partial one `status: partial` with every published identifier, both exit 1 without outputs, and no `master` tag moves unless both images verified; a missing or invalid record fails the run even after a complete publication (GB2C-01); the workflow-run evidence for the commit is resolved and authenticated, never matched by job name (GB2C-02); a failed digest validation stops before any branch is pushed. `set -euo pipefail` everywhere; no `continue-on-error`; no `|| true` on a verification path.

Workflow safety (brief section 12), enforced by `workflow_policy_check.py` and its tests rather than by convention: W1 only `push`, `pull_request`, `workflow_dispatch`, `workflow_call` (no `pull_request_target`, `workflow_run`, `schedule`, issue or comment events); W2 every job has an explicit `permissions` mapping equal to an allow-list (`contents: read` unless listed), `packages: write` appears exactly once, in a workflow whose only trigger is `workflow_dispatch`, with a concurrency group, `environment: ghcr-publish` and the master-ref guard; W3 every external action is a 40-hex commit with a version comment, local reusable workflows must exist; W4 `timeout-minutes` and `ubuntu-26.04` on every job; W5 `run:` blocks may expand only `env.*` and `runner.*` (event fields, inputs and step outputs reach the shell through `env:`; `inputs.digest` is validated by regex before use); W6 the only secret is `secrets.GITHUB_TOKEN`, no `secrets: inherit`; W7 `persist-credentials: false` on every checkout except the digest job; W8 the two ruleset-required job names exist. actionlint v1.7.12 passes; shellcheck runs in CI on both the `run:` blocks and `.github/scripts/*.sh` (it is not installed on the development host, section 13). Untrusted pull-request code runs only in read-only jobs; the privileged workflow builds from `master` after `ci` has passed for that commit and never consumes a pull request's artifacts or cache. Cleanup: the kind cluster is deleted on every path by `kind-cleanup.sh` (from the script's trap and again from the workflow's `if: always()` step), which separates the deletion request, its exit status, an independent `kind get clusters` and `docker ps -a` that must themselves succeed, and the confirmed absence; a deletion or inspection failure fails the job (exit 3 when the test had passed, the test's own status when it had failed, both reported), only a cluster named `gb-ci*` can be targeted, and every call is bounded by `timeout` (GB2C-04); `docker` containers from the image checks are removed by trap. No automatic merge, no deployment, no Kubernetes credential anywhere.

## 15. Remaining security and operational risks

- First-run risk of the hosted jobs (section 13); mitigated by fail-closed scripts and the policy that nothing is published from a pull request.
- Trivy and Syft are installed by third-party actions from GitHub release downloads; pinned by commit and version, but not verified through a checksum database the way the `go install` tools are. A later change to `go install` of both is possible (longer builds).
- `kubectl debug` under Pod Security `restricted` depends on the `--custom` merge semantics of kubectl 1.37; if the probe cannot be scheduled the job fails loudly and the node-side `/proc` and `mountinfo` evidence remains.
- The `master` tag is mutable by design (convenience); manifests never use it; `validate.py` rejects a tag.
- The publish record and SBOMs live in 90-day artifacts; a durable record belongs in the Phase 2 validation document that the operational-validation stage creates (`phase2b-handoff.md` section 13) when the first publication happens (owner or next stage).
- No signing or provenance: a consumer can verify a digest but not who built it beyond GitHub's run logs (deferred, Decision 6).
- The preflight trusts GitHub's workflow-runs and jobs API as the source of truth for the `ci` evidence (read through `GITHUB_TOKEN` with `actions: read`); it no longer trusts check-run names. A compromise of the API itself is out of scope.
- Partial publication leaves an immutable `<sha>`-tagged image for one of the two names on GHCR; the record and the operator procedure keep it visible and unreferenced, and re-dispatching for the same commit completes the pair idempotently.
- The digest pull request's sentinel comment goes stale until a human edits it (deliberate: the bot changes one line only).
- Everything live stays unproven: RWOP, NetworkPolicy enforcement, Traefik, PodMonitor, node fencing; the recovery and RWOP checklists remain **NOT APPROVED FOR EXECUTION** and Phase 2C adds no executable recovery, cleanup or deletion automation (the only deletion in the new code is of the disposable kind cluster on a hosted runner, guarded by context and name; `safety-check.py` still passes with its self-test).
