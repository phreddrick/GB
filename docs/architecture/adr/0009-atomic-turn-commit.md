# ADR-0009: Atomic turn commit with a commit record, a write fence during turns, and reload-on-failure (CR-18)

Status: Proposed 2026-11-07 (implemented locally on `feature/cr18-atomic-turn-persistence`; two independent review rounds returned CHANGES REQUIRED and were remediated on the same branch the same day, R03 accepted in the second round; **independent acceptance pending**; not deployed)

## Context

The independent review of 2026-10-27 recorded CR-18: a turn was flushed in one bbolt transaction per ship batch, star, planet and race, plus separate transactions for power, blocks, star data and the schedule (`flushAll` in `internal/game/turn.go`). A crash, `kill -9`, node loss or shutdown-budget timeout during that flush left some records at turn N+1 and others at turn N, with no stamp to detect it. Turn code also wrote news and stored telegrams to the store while the turn ran, and a panic mid-turn left the in-memory world half advanced and in use by later commands (plan 8.1). Phase 1 closed only the orderly path. The migration plan (section 8) chose, for Phase 3a, a single commit transaction per turn, a commit record, and recovery of any failure between commits by discarding memory and reloading the store (8.2), with crash-injection tests as the exit criterion (8.11).

This ADR records the first, smallest coherent slice of that design: turn-level atomicity and durability. The command staging set with group commit (8.4), per-record commit stamps, the `TURN_FAILED` mode with `RetryTurn`/`SkipTurn` (8.7), the outbox (8.9) and dirty tracking remain Phase 3a work.

## Decision

1. **One transaction per commit.** `db.Store.CommitWorld` writes, in a single bbolt transaction: every ship, star, planet and race from memory, the star data, power, blocks and power blocks, the news lines and stored telegrams the turn produced, the schedule record, and the commit record `meta/commit` `{schema_version, commit_seq, turn, segment, kind, wall_time, engine_version}`. bbolt's transaction is atomic and fsynced: the store holds either the previous commit or the new one. The three callers are the update, the movement segment and the orderly-shutdown flush (kind `update`, `segment`, `shutdown`); universe initialisation writes the first record (kind `init`, sequence 1) in its own transaction.
2. **Nothing reaches the store during a turn body, and a turn that tries is not committed (fail closed, CR18-R03).** `runTurn` captures the fence baseline, raises the store's **write fence** before the body and lowers it after: every ordinary write method, the number allocators included, returns `ErrWriteFenced`, counts the refusal and records the method name. News, stored telegrams and player-visible notifications produced by turn code are buffered on the actor and written by the commit or released after it. If the fence refused anything during the body, the turn is aborted before any commit is attempted (`gb_turns_total{result="fence_violation"}`, `gb_store_fenced_writes_total`, the method in the halt reason) and recovered like a panic; only refusals of the current turn count.
2a. **Number allocation is staged during a turn (CR18-R04).** `State.allocShipNum`/`allocCommodNum` serve a turn from an in-memory copy of the free list (pop order preserved) and then from above the highest number known to the store and to memory, so several allocations in one turn stay unique; the commit deletes exactly the popped entries (`WorldCommit.ShipFreePops`, verified against the list's tail, `ErrFreeListMismatch` otherwise). A failed turn changes no allocator state. Between turns the store's immediate allocation is unchanged.
3. **Reload-on-failure with an honest outcome (CR18-R02).** The commit is classified by the durable record, never by assumption: after an error or a panic in the transaction the record is read back; if it still shows the previous sequence, nothing was written, the buffered effects and staged allocations are dropped, the in-memory world and schedule are reloaded from the store and the engine enters `HALTED` saying so (`nothing of the turn was written; in-memory state reloaded from the last commit`); if the record cannot be read back, changed unexpectedly, or advanced although an error was reported, the engine halts with an explicit **uncertain** reason and never claims a rollback (memory is reloaded from the store as now visible when that succeeds); if the commit succeeded and only the delivery of the held notifications panicked, the engine halts saying the turn is committed and nothing was rolled back. Scheduled turns, manual turns and the shutdown commit all go through the same classification, and no panic escapes to the actor goroutine. Players connected at the time are told which of these happened.
4. **Crash semantics.** A crash at any point leaves the store at a complete commit: the previous one if the transaction had not committed, the new one if it had; never a mixture. The durable commit record at the next start says which. If the turn's commit is absent, the schedule record (committed with the world) says the turn has not happened; the existing no-catch-up policy reschedules it and the operator may run `gbctl update`. A turn is never counted twice and never half applied. This guarantee covers the turn commit; what player commands wrote per record between turns is outside it (CR-11, CR-17).
5. **Startup validation (CR18-R01).** An existing commit record must decode strictly (no unknown fields, not JSON null, not empty), carry the supported schema version, a known kind, a non-zero sequence below the overflow boundary, non-negative counters (an init record 0/0, an update record with segment 0) and a wall time; the schedule record, when present, must decode with non-negative counters; a non-init commit record without a schedule record is corrupt (they are written together), and a commit record whose turn is ahead of the schedule's can only come from a writer that bypassed the commit path. In every one of these cases the engine starts `HALTED` with reason `CORRUPT_STORE…`, alive but not ready, writes nothing (no fresh schedule is created over corrupt committed state) and the operator decides (the dedicated `CORRUPT_STORE` mode of plan 8.7 is deferred; `HALTED` carries it). An absent commit record (a store written before this change, such as the development universe initialised on 2026-11-07) is accepted and its first commit creates the record; an init record without a schedule is the supported fresh-universe case; a schedule ahead of the commit record means turns were persisted by an older binary and is accepted with a warning.
6. **Observability.** `gb_commits_total{kind,result}`, `gb_commit_duration_seconds{kind}`, `gb_commit_seq`, `gb_store_fenced_writes_total`; `commit_seq` in `gbctl status`; `turn complete` logs the sequence; the status persistence note states the new guarantee and the remaining per-command limitation. `db.Store.WorldDigest` is the logical-state digest of plan 8.8 (world buckets, universe and schedule records without `saved_at`, commit sequence and counters) used by the tests.
7. **Not changed.** Game rules, turn order and formulas; the per-record writes of player commands between turns (CR-11 and CR-17 remain separate open findings: the six `store.GetPlanet` sites and the 70 `Put*` sites are untouched, so a command that fails between two of its own writes is still not atomic, and not every database mutation is turn-atomic); ship reload from the store at turn start; the no-catch-up schedule policy; the admin API. Live notifications are best-effort after the commit.

## Alternatives considered

- **Wrapping only `flushAll` in one transaction.** Rejected as incomplete: news, telegrams and any future direct write during the body would still leak before the commit, and a panic mid-body would still leave memory half advanced for the next command. The fence and the buffers close the first; reload closes the second.
- **Staged working copy or copy-on-write for turns** (plan 8.2 table). Rejected for now: a correct deep copy of every model type is error-prone and unnecessary at this world size; reload from the committed store is simpler and is exercised by every startup.
- **Dirty tracking to write only changed records.** Deferred: writing the whole world (627 planets, 100 stars) in one transaction is one fsync and measured well inside the Phase 3a budget on local disk; dirty tracking belongs with the staging set.
- **Refusing to start on a schedule ahead of the commit record.** Rejected: it would turn a rollback to the previous image plus a roll-forward into an outage with no repair tool; the condition is not evidence of a half-applied turn.
- **A `faultinject` build tag for the test hooks.** Rejected for this slice: tests must run under the plain `go test ./...` the gates use; the hooks (`SetCommitFault`, the mid-turn test hook) are exported or package-private and documented as test-only, following the existing `GB_TEST_HOOKS` pattern.

## Consequences

- A completed turn is durable as one consistent state transition; an interrupted turn is never exposed as committed and never leaves a partially updated world. `gb-dev` data stops being disposable for *turn* persistence; it remains disposable for *command* persistence until the staging set and group commit land. CR-18 is **implemented, independent acceptance pending**: the inventory entry `persistence/non-atomic-turn-flush` stays until the reviewer accepts the corrected implementation.
- Segment commits now also persist star data, power and blocks (previously only full updates did). Star data carries the orbit-chain root that segments rebuild, so this is a correction, not a rules change; the values are idempotent otherwise.
- Player-visible turn output (bulletins, discoveries, "Finished with update") appears after the commit instead of during the turn. The start banner is still sent before the body.
- A telegram to a governor who is online when the turn generates it is delivered after the commit and not stored; if that governor disconnects between generation and commit, the live delivery fails silently, as it did before (the C server has the same window).
- A turn-time code path that writes to the store directly now aborts the turn (refused, counted, named in the halt reason) instead of either a silent partial write or a commit that silently lacks the refused news line or telegram.
- A shutdown that times out does not claim the running turn was or was not persisted: the turn may still commit after the exit, and the durable commit record (`commit_seq`) at the next start says which commit the store holds.
- The `HALTED` reason after a failed turn distinguishes a reloaded (consistent) memory from an untrusted one; the operator response (restart, then `gbctl status`) is unchanged.
- Rolling the development deployment back to the pre-ADR image is safe for the store; rolling forward again is accepted with a warning.

## Validation

`go/internal/db/commit_test.go` (commit round trip, injected fault before and after writes rolls back everything, record validation, strict decoding of both meta records with the absent-versus-malformed distinction, fence coverage of every write method including the allocators, staged free-list pops verified against the list, digest stability across reopen), `go/internal/game/commit_remediation_test.go` (every malformed-metadata case starts HALTED/CORRUPT_STORE without a write; supported legacy cases; panic inside the transaction; panic after the transaction committed classified as uncertain; notification panic after a successful commit; a failing scheduled turn; shutdown-commit panics classified; staged allocation rolled back on panic and on commit error, unique across a turn without insertion for both number spaces, committed and continued after restart; commodity allocation; between-turn allocation unchanged; the second review's metadata, disappeared/malformed/altered-record and reload-failure cases) and `go/internal/game/commit_test.go` (T1-style panic after mutations: store digest unchanged, memory reloaded, effects dropped, halted, clean restart, no duplicate turn; commit failure after all records were put; direct write during a turn refused and counted; shutdown commit and its failure; restart preserves counters, digest and commit sequence; universe identity and race identity across commits and restarts; corrupt store refused at startup; legacy and schedule-ahead stores accepted; online/offline telegram handling; 100-star segment commit timing). `go/test/e2e/crash_test.go` kills a real `gb-server` with `SIGKILL` during the turn body (before any transaction is open) and, in a second test, exits the process from inside the open commit transaction at both fault stages; both assert the store equals the last commit, restarts cleanly without `CORRUPT_STORE`, counts no turn, and commits the next update. The known-defect entry `persistence/non-atomic-turn-flush` reads IMPLEMENTED - INDEPENDENT ACCEPTANCE PENDING. Remaining plan 8.11 items not covered here: a crash inside bbolt's own page-write path (no hook exists; bbolt's documented atomicity is relied upon), T4–T6 and T11–T12 (command staging and group commit), T7 (disk full in `kind`), T9 (determinism, Phase 3b), T10 (restore, snapshot stream).
