# ADR-0008: Explicit universe bootstrap through the admin API; development data recovered by volume replacement, never by an overwrite option

Status: Proposed 2026-10-30 (Phase 2B draft for owner review)

## Context

Phase 1 made universe creation an explicit, seeded, single-transaction admin operation (`gbctl universe init -seed N ...`) that is refused with HTTP 409 (exit 4) on an initialised store, and deliberately shipped **no overwrite path**: `docs/operations/local-server.md` section 3 says so, and `phase1-validation.md` flagged that the migration plan's Phase 2 rollback text still named `gbctl universe init --force --seed <seed>`. Neither `gbctl` nor the admin API has such an option. The old `k8s-deployment.yaml` regenerated the universe from an init container on every pod start (CR-05); that pattern is the failure this ADR rules out. The engine starts on an empty volume in `UNINITIALIZED` with `/readyz` 200 and `game_ready:false`, so a fresh pod can be initialised through a port-forward without a restart loop.

## Decision

1. **Bootstrap is an operator command, never a hook, init container or sidecar.** No `PreSync`/`PostSync` hook, no init container and no Job mounts the `world` volume. After `gb-dev-server` is synced and the pod is Running in `UNINITIALIZED`, the operator runs `gbctl universe init -seed <N> -stars <S> -min-planets <a> -max-planets <b>` against the admin listener through `kubectl port-forward pod/gb-engine-0 8081:8081` (or a one-off `kubectl run` of the `gbctl` image inside the namespace, which the NetworkPolicy would need to admit; port-forward is the default). The token comes from `GBCTL_TOKEN_FILE`; it is never a command-line argument.
2. **The seed is the backup.** The operator records seed, star count, planet bounds, generator version and the `initialized_at` timestamp printed by `gbctl` (and stored in `meta/universe`) in the operations log the moment the universe is created. Until Phase 3a this record is the only data-recovery mechanism, and the runbooks say so.
3. **No destructive option is added to `gbctl`.** `universe init` keeps refusing an initialised store. Re-initialisation always goes through a **new, empty volume**.
4. **Development-volume recovery is specified as an operator planning checklist, not as an executable procedure** (`docs/operations/dev-volume-recovery.md`, marked NOT APPROVED FOR EXECUTION). Revised 2026-10-30 through four independent reviews (GB2B-03, GB2B-03R, GB2B-02R, GB2B-04, GB2B-05, GB2B-06): the executable shell helper library and its test suite that the intermediate revisions introduced were retired from Phase 2B after the fourth review, because repeated defects in executable recovery automation are not acceptable in a stage whose deliverable is artifacts (`docs/testing/phase2b-handoff.md` section 12.9). The checklist keeps the safety requirements as requirements: entry by the engine's actual condition (a responsive engine is quiesced first, `gbctl quiesce` being applied at an actor operation boundary and waiting behind a running turn; a **HALTED** engine can be neither quiesced nor resumed and is stopped as it is, its store treated as possibly partially updated; an **unreachable** engine is never assumed stopped); identification of every potentially surviving writer by UID (controller ownerReference, ControllerRevision, every engine-labelled Pod, Pod UIDs in Events, with the statement that Events are an incomplete history); control of competing reconcilers inside a written maintenance window; the desired replica count verified at zero **before** any stale Pod object is cleared (otherwise the controller recreates `gb-engine-0` on the same claim while the old writer may still run); a replacement writer only after independently verified fencing (power-off held, or on-node verification that the `containerd-shim` and `gb-server` process are gone with restart prevention verified by effective state, or a kubelet-confirmed graceful deletion), since `NotReady`, a missing Pod object, a forced-deletion response, stopped kubelet, containerd or RKE2 services, lost SSH, a cordon, a detached-looking volume, a silent admin endpoint and the disappearance of any API object prove nothing about a process; attachment verified by both the VolumeAttachment list and the Longhorn volume, each well-formed; the original claim protected and re-identified at every gate; evidence recorded as data, never as shell assignments or sourced files; unknown, contradictory or missing evidence always STOP; a writer that cannot be identified or fenced leaves recovery BLOCKED; and the home lab has no demonstrated remote power fencing. The planned operations, each separately approved, are then:
   1. Stop the process (desired replica count to zero) and confirm no attachment remains; the retention policy keeps `world-gb-engine-0`.
   2. Protect the old volume: annotate the PVC with a retirement marker and the reason; if anything on it might matter, take a Longhorn snapshot or backup first.
   3. Retire it only on the owner's explicit, written authorisation naming the claim's UID: the deletion of the claim is issued by hand (the `longhorn` class deletes the data). Kubernetes cannot rename a PVC and the claim-template name is frozen, so keeping the old claim under the same name is impossible; keeping it under another name would change the frozen identity and is not done.
   4. Desired count back to one: the StatefulSet controller provisions a fresh `world-gb-engine-0` (a new object with a new UID and PV; the old volume is never reused or cleaned in place); the engine starts `UNINITIALIZED`.
   5. `gbctl universe init` with the recorded seed and parameters reproduces the identical universe (seeded generation, Phase 1); verify the printed record against the log; a second `init` must return exit 4.
5. **Orderly restarts keep the data.** `kubectl rollout restart statefulset/gb-engine` after `gbctl quiesce`, or a pod deletion while no turn is due, exercises the exit-0 path (sessions closed, turn finished, flush, schedule persisted, store closed) and preserves universe and schedule. A crash, `kill -9`, exit codes 2, 3 or 6, or a node loss mid-turn may leave a mixed-turn store (CR-18); the response is the recovery procedure above, not a repair.

## Alternatives considered

- A guarded `gbctl universe init --force --confirm <id>` that takes a safety snapshot first (plan 12.5 item 4): deferred to Phase 3a, where the snapshot stream and commit record exist; without them "force" is an overwrite without a safety net.
- Deleting the database file in place from a debug container: no shell in the image, needs a privileged ephemeral container with the volume, and leaves the pod identity and PVC in an ambiguous state; rejected.
- An init container that runs `makeuniv -skip-if-initialized`: idempotent, but it reintroduces a second process touching the store (CR-03/CR-05 lineage) and hides the moment of creation from the operator; rejected (plan 12.5 item 6).

## Consequences

- Recovery deletes data by design and therefore needs the owner's word each time; this is the intended friction for the only destructive step in the Phase 2 documents.
- Recovery is **unimplemented as an executable procedure** in Phase 2B. Until the checklist has been independently reviewed and rehearsed in the separately authorised operational-validation stage, a `gb-dev` failure is answered by preserving evidence and asking the owner, not by any scripted or ad-hoc recovery; `deploy/kustomize/tests/safety-check.py` fails if executable recovery or deletion automation reappears in the artifacts.
- The plan's Phase 2 rollback text and 12.5 item 4 are amended to this procedure (2026-10-30).
- `gb-dev` must be treated as disposable until Phase 3a; nothing here promises crash consistency.

## Validation

Phase 2 acceptance: `gbctl universe init` succeeds once on the fresh volume and is refused (exit 4) on the second attempt; three orderly restarts and one drain preserve universe and schedule. The recovery checklist is rehearsed against a throwaway StatefulSet in the operational-validation stage, never first on `gb-dev`, and its result recorded before the owner approves it for use (`dev-volume-recovery.md` section 10). `deploy/kustomize/tests/validate.py` fails on any init container or hook-annotated object; `safety-check.py` fails on any runnable recovery or deletion automation in the artifacts.
